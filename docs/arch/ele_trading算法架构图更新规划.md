项目已从“`trading/` 承载规则、契约、策略、结算、回测和编排”的大包结构，重构为模式接口化分层：

```text
domain ← markets ← positions / operations ← trading ← backtest
```

本次更新应让两张图准确表达新结构：

1. 技术图准确展示包职责、允许的依赖方向、活动主链与独立边界。
2. 业务图保持纯业务语言，准确展示单结算主线、需求响应闭环、回测评价和规则模式边界。
3. 两图使用同一事实基线，但分别回答“系统由什么组成”和“业务如何运行”，不重复堆叠同一层信息。
4. 消除旧目录、旧地区活动命名、错误模块归属和中心绑定箭头。

## 2. 新架构事实基线

### 2.1 项目级双包边界

项目当前有两个平级、职责不同的 Python 包：

| 包 | 定位 | 依赖边界 |
|----|------|----------|
| `src/ele_trading/` | 电力市场交易、运行调度、规则结算、回测 | 活动交易主包 |
| `src/investment_estimation/` | 风光储投资收益测算、容量搜索、财务指标、资源仿真 | 完全自包含，不依赖 `ele_trading` |

技术图应把 `investment_estimation` 画成项目级独立边界，标明“平级自包含、不进入交易主链”，不得再出现
`ele_trading/capacity_planning`。业务图聚焦电力交易生命周期，不展开投资测算。

### 2.2 `ele_trading` 责任分层

| 层/包 | 新职责 | 不再承担的职责 |
|-------|--------|----------------|
| `domain/` | 市场无关领域契约、交易事件契约 | 市场参数、结算公式、求解逻辑 |
| `markets/` | 按结算模式组织的规则插件和共享结算工具 | 头寸策略、运行优化、主链编排 |
| `positions/` | 中长期仓位、月度分解、竞价阶梯与量价走廊 | 市场配置加载、结算、日内运行 |
| `operations/` | 日前物理运行计划、日内滚动、主链需求响应联合优化 | 编排、回测、市场规则定义 |
| `trading/` | `TradingOrchestrator` 和 demo fixtures | 契约、规则、头寸、运行、结算、回测实现 |
| `backtest/` | walk-forward 回放、策略对照和交易/BESS 指标 | 活动交易编排实现 |
| `demand_response/` | 独立事后经济性评估工具 | 主链 DR 联合优化与履约结算 |

结构守卫的硬方向为：

```text
领域契约
   ↑
市场规则插件
   ↑
头寸决策 / 运行计划
   ↑
交易编排
   ↑
回测评价
```

其中：

- `demand_response` 是品种层，可依赖 `domain/markets`。
- `forecasting → scenario → optimization` 构成预测、不确定性与数学内核支撑链。
- `operations` 使用 `domain/markets/scenario/optimization`。
- `trading` 注入数据、预测、场景、配置和求解器，编排单结算主线。
- `backtest` 驱动 `trading` 做无前瞻回放，并调用必要的运行与结算能力生成对照组。

### 2.3 市场规则模式

`markets/` 当前包含：

| 模式 | 状态 | 图中表达 |
|------|------|----------|
| `single_settlement` | 活动主线 | 实线接入交易编排和业务结算阶段 |
| `dual_settlement` | 已实现并有测试的规则引擎，未接主链编排 | 旁路插件卡片，明确“已实现 / 未接主链” |
| `shared` | 两种模式共享的结算时段聚合工具 | markets 容器中的共享底座，不单独进入业务流程 |

规则插件按**结算模式**命名，不按地区命名。蒙西只作为规则研究背景：

- 技术图不得出现活动节点 `settlement_mengxi`、`market_mengxi.yaml`、`config_loader` 属于 `trading/` 等旧表达。
- 业务图可以保留“蒙西电力交易算法”图名，但内部活动节点使用“单结算规则口径”。
- 双结算不进入活动七阶段主链，只作为可替换规则模式说明。

### 2.4 活动单结算运行链

```text
持仓状态
  → 四路预测（电价、负荷、风电、光伏）
  → 联合场景
  → 日前物理运行计划（可含需求响应联合优化）
  → 日内冻结已执行段并滚动重排
  → 单结算报告
  → walk-forward 回测与评价
```

关键事实：

1. `TradingOrchestrator` 编排持仓读取、预测、场景、日前、日内和结算；中长期/月度策略有独立入口，不能画成 orchestrator 内部实现。
2. 日前价格只可作为运行解释信号，不进入财务结算。
3. 需求响应主链逻辑位于日前联合优化、日内履约约束和单结算履约核算三个阶段；
   `demand_response/allocator.py` 只是独立事后评估工具。
4. 真值只在决策完成后进入结算和明确标识的理想上限对照。
5. 15 分钟颗粒度使用 `dt = 0.25`。

## 4. 技术架构图修改规划

### 4.1 目标标题与副标题

- 标题：`ele_trading 电力交易算法架构`
- 副标题：`模式接口化分层｜单结算活动主线｜双结算规则插件未接主编排`

删除标题中的“蒙西单结算 · v2 实现现状”，避免把地区、结算模式和版本状态混成一个层级。

### 4.2 目标版式

采用“中央责任分层 + 左侧数据与不确定性支撑 + 右侧优化内核 + 底部项目边界”的布局：

```text
┌────────────────────────────── 入口层 ──────────────────────────────┐
│ app/trading · app/optimization · investment_estimation/app         │
└─────────────────────────────────────────────────────────────────────┘

┌──────── 数据支撑链 ────────┐  ┌──────── 交易责任分层 ────────┐  ┌── 数学内核 ──┐
│ data_provider               │  │ backtest                      │  │ optimization │
│      ↓                      │  │      ↓                        │  │ BESS / MPC   │
│ forecasting                 │  │ trading（仅编排）             │  │ CVaR / solver│
│      ↓                      │  │      ↓                        │  └─────────────┘
│ scenario                    │  │ positions / operations        │
└─────────────────────────────┘  │      ↓                        │
                                 │ markets（模式插件）            │
                                 │      ↓                        │
                                 │ domain（领域契约）             │
                                 └───────────────────────────────┘

┌──────── 配置 / utils ────────┐  ┌─ investment_estimation ──────────┐
│ configs/markets · configs/... │  │ 平级、自包含、投资收益测算       │
└───────────────────────────────┘  └──────────────────────────────────┘
```

布局原则：

- 中央纵向明确责任层级，消费者在上、依赖在下。
- 左侧支撑链用实线表达数据演进：数据快照 → 预测结果 → 场景集。
- 右侧优化内核只连接 `operations`，不直接连接市场规则或回测。
- `dual_settlement` 放在 `markets` 容器内，与活动 `single_settlement` 并列，但使用虚线边框和“未接主链”状态。
- `investment_estimation` 使用独立容器，不与 `ele_trading` 主链画依赖箭头。

### 4.3 必须出现的节点

#### 入口层

- `app/trading/`：中长期、月度、日前、日内、需求响应、回测、统一编排入口。
- `app/optimization/`：套利、MPC、Two-stage + CVaR 示例入口。
- `investment_estimation/app/`：容量搜索、MVP、资源仿真与迁移暂存入口。

#### 中央责任层

- `backtest/`：walk-forward 回放、四组对照、指标。
- `trading/`：`TradingOrchestrator`、`demo_fixtures`，并明确“仅编排”。
- `positions/`：中长期仓位、月度竞价与量价走廊。
- `operations/`：日前计划、DR 联合优化、日内滚动与物理回退。
- `markets/`：
  - `single_settlement`：活动配置、结算报告、单结算、DR 履约结算。
  - `dual_settlement`：双结算与偏差带考核，已实现、未接主链。
  - `shared`：结算时段聚合。
- `domain/`：领域契约、事件契约、追溯信息。

#### 支撑层

- `data_provider/`：版本化数据快照、质量控制、资产与气象接入。
- `forecasting/`：五类预测统一门面与无未来信息检查。
- `scenario/`：联合场景、LHS/MC、Wasserstein L1 后向缩减。
- `optimization/`：BESS 物理核、套利、MPC、Two-stage + CVaR、typed 求解状态。
- `demand_response/`：独立事后经济性评估；明确不等于主链 DR 联合优化。
- `configs/`、`utils/`：配置注入和无业务语义工具。

### 4.4 箭头规则

技术图同时存在运行数据流和依赖关系，必须在图例中区分：

- **实线**：运行时数据或控制流。
- **虚线**：配置注入、规则约束或静态依赖。
- 箭头不带文字，输入/输出写在目标节点内部。
- 依赖箭头统一指向被依赖层，例如 `markets → domain`、`trading → operations`。
- 运行主链统一从左到右或从上到下，不得与依赖箭头反向混走同一走廊。
- 不使用中心绑定的 elbow 箭头；使用显式边界坐标和专用水平/垂直走廊。

### 4.5 明确禁止出现的旧节点

```text

trading/monthly_trader
trading/day_ahead_coupled
trading/intraday_rolling
trading/settlement_mengxi
trading/backtest
trading/metrics
trading/sample_data
configs/trading/market_mengxi.yaml
src/ele_trading/capacity_planning
```

## 5. 业务架构图修改规划

### 5.1 标题层

- 主标题保留：`蒙西电力交易算法 · 业务架构`。
- 副标题改为：`单结算模式主线（规则研究参考蒙西）｜决策—执行—结算—评估闭环｜15 分钟颗粒度`。
- 通过副标题区分“业务适用背景”和“活动模块命名”。

### 5.2 七阶段主链目标内容

| 阶段 | 输入依据 | 核心动作 | 业务输出 |
|------|----------|----------|----------|
| 01 市场数据准备 | 历史电价、统调负荷、风光与气象、合约成交 | 截止决策时点完成质量校验和版本固化 | 版本化市场快照与当前持仓状态 |
| 02 市场预测 | 决策时点可用数据 | 形成 96 点电价、负荷、风电、光伏点预测与区间 | 四路预测及数据/模型版本 |
| 03 不确定性量化 | 预测误差、分位区间、相关关系 | 联合生成并缩减场景，保留尾部与关键事件 | 代表场景、概率权重、尾部风险 |
| 04 中长期与月度决策 | 持仓缺口、预算、价格区间、风险边界 | 年度覆盖、月度分解、集中竞价或量价走廊 | 目标仓位、竞价阶梯、再平衡建议 |
| 05 现货日前运行计划 | 当前持仓、预测场景、储能状态、响应规则 | 次日 96 点充放电；无响应基线与响应增量联合决策 | 日前物理计划、风险敞口、响应承诺 |
| 06 日内滚动调整 | 最新预测、实际执行、剩余荷电状态、响应承诺 | 冻结已执行段，重排剩余窗口并保证响应履约 | 最新可执行计划、调整原因、回退标记 |
| 07 结算与经营复盘 | 实际电量、实时价格、履约记录、规则口径 | 单结算逐项核算、储能增量收益与偏差归因 | 结算报告、策略档案、回测输入 |

### 5.3 左侧决策边界

保留三组能力，但更新命名和内容：

1. **无未来信息纪律**
   - 只使用决策时点已发布数据。
   - 预测、场景、决策和回测按版本留痕。
   - 仅“理想上限”对照允许使用未来真值。

2. **交易与风险边界**
   - 持仓上下限、交易最小单位和价格边界。
   - 预算与风险敞口。
   - 尾部损失和求解失败处理。

3. **储能物理与寿命边界**
   - 荷电状态、充放电功率和效率。
   - 禁止同充同放、吞吐量和末端荷电状态。
   - 退化成本、循环次数与寿命影响。

### 5.4 右侧闭环能力

#### 需求响应闭环

按主链真实分工改为三段：

1. **日前申报**：无响应基线、增量响应、补偿收益与机会成本共同判断。
2. **日内履约**：已执行电量与剩余窗口共同约束，失败时执行物理可行回退。
3. **结算核算**：按实际增量计算补偿，按未履约量计算罚金。

右栏仅用业务语言，不出现 `operations`、`compute_dr_settlement` 等代码名。

#### 单结算规则口径

节点标题改为“单结算规则口径”，内容保持：

- 实时电能 + 中长期差价 + 长协回收。
- 需求响应、退化成本和执行分项分别列示且不重复计费。
- 日前价格只作运行参考，不参与财务结算。
- 小字注明“规则研究参考蒙西市场规则”。

#### 可扩展规则模式

新增独立说明卡，不接入活动主线：

- “双结算与偏差带规则引擎”。
- 状态：“已实现并测试，未接活动交易编排”。
- 使用虚线边框，避免被误认为现役结算步骤。

#### 历史回测与策略评价

- 逐日重放完整决策链，严格遵守无未来信息。
- 对照组：无储能、确定性策略、风险策略、理想上限。
- 评价收益、风险、回退、约束与退化。

### 5.5 底部经营评价

继续保留四组指标：

- 经济性：储能增量收益、需求响应净收益。
- 风险性：尾部损失、偏差与风险敞口。
- 可执行性：计划回退、求解状态、约束触发。
- 资产影响：等效循环、雨流退化与寿命成本。

其中等效循环必须以正确储能容量为基准；雨流退化必须使用完整荷电状态序列。

## 6. 两图一致性矩阵

| 业务图内容 | 技术图责任节点 | 一致性要求 |
|------------|----------------|------------|
| 市场数据准备 | `data_provider` + `domain.PositionState` | 表达版本、截止时点和质量边界 |
| 市场预测 | `forecasting` | 四路活动预测；天气能力是支撑，不进入 orchestrator 四路结果 |
| 不确定性量化 | `scenario` | 默认 LHS、保留 MC；Wasserstein L1 后向缩减 |
| 中长期与月度决策 | `positions` + `markets` 配置 | 是独立策略入口，不画成 `TradingOrchestrator` 内部函数 |
| 日前运行计划 | `operations` + `optimization` + `markets/single_settlement` | 物理计划，不是财务日前仓位 |
| 需求响应 | `operations` + `markets/single_settlement` | 主链联合优化、日内履约、结算核算三段；allocator 仅独立评估 |
| 日内滚动 | `operations` + `domain` | 冻结已执行前缀、失败物理回退 |
| 单结算 | `markets/single_settlement` + `trading` 编排 | 日前价不结算，逐项不重复计费 |
| 双结算扩展 | `markets/dual_settlement` | 已实现、未接主链，不进入业务七阶段 |
| 回测评价 | `backtest` → `trading` | 回测驱动完整编排，不属于 `trading` 内部实现 |
| 经营指标 | `backtest/metrics` | 正确容量、完整荷电状态、风险和退化并列 |
| 决策追溯 | `domain.DecisionTrace` | 贯穿预测、求解、回退、结算与回测 |

### 阶段 C：更新业务架构图

## 8. 视觉与几何规范

两张图共同遵守：

- 不使用圆形节点；阶段编号写入标题条。
- 大模块使用“外框 + 标题条 + 小内容块”，避免单个大文本框。
- 同类模块使用统一宽高、内边距和间距；不允许肉眼近似对齐。
- 箭头统一使用直线或正交折线，禁止曲线穿越模块。
- 箭头端点落在模块边界；不得使用默认中心锚点产生穿盒路径。
- 复杂路径拆成显式水平/垂直线段，只在末段保留箭头。
- 运行流和依赖流使用独立走廊，箭头不交叉、不重叠、不贴盒边长距离行走。
- 箭头本身不带标签；输入、处理、输出和状态写在节点内部。
- 业务图只用业务语言；技术图允许包名和契约名。
- 同一事实只出现一次，其他位置用短说明或箭头关系表达。

建议几何基准：

- 容器内边距统一 `16 px`。
- 同级卡片间距统一 `12 px`。
- 主列阶段间距统一 `70 px` 以上。
- 主列与侧栏保留 `120 px` 以上专用走廊。
- 标题、列标题和容器边界使用同一左对齐基线。
