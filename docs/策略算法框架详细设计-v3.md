## 2. 问题定义

v3 的主要目标是优化当前已实现算法的架构、公共契约和实现细节，使物理约束、市场策略、求解、编排和回测之间的边界更清晰。v3 不以继续增加算法数量为主要目标，也不把旧版本的目录、Phase 或实现选择自动视为新版本约束。

算法层功能增强（预测精度、场景真实性、风险度量、报价能力等）不属于本文范围，由 [策略算法框架详细设计-v4.md](策略算法框架详细设计-v4.md) 承载；v4 引用的架构边界以本文决策记录为准。

## 5. v3 强制业务不变量

以下约束对 v3 设计和实施均有效：

1. **无前瞻**：决策只能消费决策时刻可获得的数据；预测、特征和场景必须记录实际来源时刻与版本。
2. **时间与单位明确**：时间戳必须明确时区；功率、电量、价格、频率和 `dt` 必须在契约边界声明并一致换算。
3. **市场参数注入**：市场规则、价格限制、考核系数和风险参数不得隐藏在通用算法实现中。
4. **结算唯一计费**：电能、合同差价、回收、DR、退化和执行调整必须有唯一计费归属，不得重复计入。
5. **数据边界**：样例、fixture 和模拟数据只能用于接口、demo 和回归，不能直接作为生产策略评估数据。
6. **失败透明**：求解失败必须返回显式状态或进入有记录、可解释的受控回退，不得伪造成功计划。
7. **事件可追踪**：交易链各阶段的决策证据以事件链承载（Forecast→Bid→Award→Dispatch→Metering→Settlement），任一决策可回溯到输入版本、配置版本和求解状态。

## 7. 目标架构

### 7.1 领域契约

`domain` 保持全项目最底层契约层，只允许依赖标准库/pandas，结构守卫测试维持不变。

- 稳定领域对象：`PositionState`、`MarketForecastBundle`、`OperationalPlan`、`IntradayPlan`、`DRCommitment`、`DecisionTrace` 保持现有语义，只做增补性扩展。
- 事件契约落地：`TradingEvent` 族（Forecast/Bid/Award/Dispatch/Metering/Settlement）补全市场日历、交割时段和单位字段；`DecisionTrace` 改由事件链生成，不再由编排器手工拼装（D-006）。
- 版本兼容边界：契约字段只增不改；语义变化必须升 `schema_version` 并记录迁移方式。

### 7.2 数据与预测

- 生产数据 adapter 归 `data_provider`；样例数据只作 fixture（不变量 5）。
- 预测 registry 保持统一 `ForecastRequest`/`ForecastResult` 契约。
- 市场/组合负荷预测归 `forecasting`：扩展 load target 的多层级（系统/区域/节点/组合/场站）与层级协调，历史不足时输出明确降级标识（D-001 市场轨）。
- 历史 forecast vintage 是无前瞻回测的必要输入；只有观测真值时不得宣称完成无前瞻回测。
- 用户侧需量预测不归 `forecasting`，归属用户侧领域包（见 §7.9）。

### 7.3 场景与风险

- canonical API 唯一：`ScenarioSet` + `build_joint_scenarios`（D-007）。
- 采样默认 LHS，保留 `method="mc"`；相关性结构首版维持可解释的残差相关，替换相关结构不得改变 `ScenarioSet` 契约。
- 缩减固定 Wasserstein/Kantorovich L1 后向缩减，权重重新归一化，并输出诊断：权重和为 1、边际均值/分位偏移、关键价差与净负荷峰值覆盖、同 seed 可复现。
- legacy `PriceScenario`/`generate_price_scenarios` 进入弃用期（见 §10.2）。
- 场景与风险优化的接口：缩减后 `ScenarioSet` 直接传入风险模型，禁止孤立演示。

### 7.4 通用物理与求解内核

模型构建统一拆为四层（D-004、D-005）：

1. **公共物理核**：`optimization.bess_model` 的 `BESSConfig` + `add_bess_constraints` 是唯一 BESS 状态转移与约束实现，覆盖 SOC 动态、效率、功率、充放互斥、终端 SOC、吞吐量和禁止反送；`mpc_bess` 迁入共享核并删除私有约束，主链 `dt` 统一 0.25。
2. **目标策略层**：各模型的目标函数（套利、CVaR 风险、履约、DR）作为可组合的目标组件，与物理约束解耦；市场规则参数经配置注入（不变量 3）。
3. **统一求解 adapter**：`optimization.solver` 的 `SolveStatus`/`SolverResult`/`solve_pulp_model` 是所有模型的唯一求解出口，负责求解器选择、时限、容差和状态归一化。
4. **统一结果提取**：求解结果到领域对象（`OperationalPlan` 等）的提取逻辑单点实现；求解失败返回显式状态或受控回退（不变量 6）。

日前、日内、Two-stage 三个模型文件各自只保留参数组装与调用编排。

### 7.5 市场策略

市场模式 Protocol 是 v3 的核心新增接口（D-002）：

- `markets/<模式>/` 插件自包含：配置契约、加载校验、结算引擎、头寸策略、运行策略、编排与回测注入点。
- 主链（`trading`/`backtest`）只依赖 Protocol，不再直接 import 具体模式包。
- 单结算为默认活动模式；双结算经 Protocol 注入接入主链，不修改主链代码。
- 市场规则、头寸策略、报价策略、DR 产品和结算策略之间的依赖方向：结算与规则归插件，策略可插拔，通用物理与求解不感知市场语义。

### 7.6 日前与日内运行

- 日前计划、滚动重优化、冻结前缀、履约约束和受控回退为 `operations` 的共用能力，对市场模式的差异通过注入的策略与配置体现。
- 日内滚动每次重优化必须消费决策时刻最新的 forecast vintage（不变量 1）。
- 求解失败回退到上次可行计划并经物理边界裁剪后执行，回退事实进入事件链与 `DecisionTrace`。

### 7.7 编排与结算

- 编排器改为纯依赖注入：数据、预测、场景、策略、结算和事件记录全部经构造注入，市场模式选择由配置驱动。
- 结算唯一计费（不变量 4）：电能、合同差价、回收、DR、退化、执行调整逐项列示且只计一次。
- 决策追踪事件化：编排器发出 Forecast/Dispatch/Settlement 事件，`DecisionTrace` 由事件链生成（D-006）。

### 7.8 回测与评估

- walk-forward 时间契约：只消费决策时刻已发布的数据与预测 vintage；oracle 基准是唯一能使用真实未来价格的对照组。
- 基准组：无储能、确定性策略、风险策略、oracle 四组保持。
- 业务反例：数据缺失、模型失败、求解失败、物理不可行四类必须有专门回归用例。
- 性能预算见 §10.4；生产评估必须基于真实数据与真实规则标定，样例结果不构成收益结论（不变量 5）。

### 7.9 用户侧需量领域

D-001 决策为双轨，`user_side_dispatch` 恢复为活动独立领域包：

- 承载用户侧需量控制能力：最大需量口径（固定/滑动窗口，配置显式决定）、`D_cap` 决策（月末/月初/月中/每日/每小时分层）、需量电费核算和用户侧储能调度。
- 与市场交易主链隔离：不进入交易编排链，不共享 `MarketConfig`；与市场轨的连接点是 `forecasting` 的负荷预测能力。
- 恢复范围：`interfaces.py`（513 行）、`algorithms/` 六个算法文件、`adapters/`、四个 `app/user_side_dispatch/` 入口和 `configs/user_side_dispatch/` 配置，全部重新接入活动测试。
- `需量预测算法设计方案-v0.md` 的口径与分层策略在恢复实施时重新评审激活，其中“待确认问题”清单转为实施前置条件。

## 10. 迁移与兼容策略

### 10.1 迁移阶段

按“契约与回归基线 → 共享物理核 → 配置拆分 → 模型构建边界 → 策略接口 → 编排与回测事件化 → 用户侧恢复”执行；每一阶段合并前 active-only 回归基线必须保持绿色。

| 阶段 | 输入 | 输出 | 兼容面 | 退出条件 |
|---|---|---|---|---|
| M0 契约与回归基线 | 当前 366 passed 基线、公开 API 清单 | 基线冻结记录；事件字段补全（市场日历、交割时段、单位）；legacy 场景 API 标记 `DeprecationWarning` | 无行为变化 | 基线可复现；弃用告警生效 |
| M1 共享物理核 | `bess_model` 共享核、`mpc_bess` 私有实现 | MPC 迁移到共享核，私有约束删除，`dt` 口径统一 0.25 | `run_bess_mpc`/`solve_one_mpc_window` 签名保持 | 新旧 MPC 数学等价回归一致 |
| M2 配置拆分 | 40 字段 `MarketConfig`、现有 YAML | 六子对象 typed config + `schema_version`；loader 分区段装配 | 旧 YAML 经迁移脚本转换，不留双格式 | 配置测试重写完成；366 基线绿色 |
| M3 模型构建边界 | 日前/Two-stage/日内三个厚模型 | 目标策略层 + 统一求解 adapter + 统一结果提取；三模型只留组装逻辑 | 公开函数签名保持 | 数学回归（目标值、约束激活）与拆分前一致 |
| M4 市场模式 Protocol | 五包对 `single_settlement` 的直接依赖 | `MarketMode` Protocol；五包改依赖注入；双结算经 Protocol 可接入 | 单结算默认行为不变 | 结构守卫证明主链无具体模式 import；366 基线绿色 |
| M5 编排与回测事件化 | 手工拼装的 `DecisionTrace` | 编排与回测事件驱动；`DecisionTrace` 由事件链生成 | `TradingPipelineResult` 字段只增不改 | 任一决策可回溯事件链；回测四基准结果不退化 |

M2 与 M3 可并行；M4 依赖 M2（配置子对象是 Protocol 的配置注入面）；M5 依赖 M0（事件字段补全）；M6 与 M1–M5 无依赖，可独立排期。

### 10.3 测试策略

测试分六类，归属明确：

1. **业务不变量**：无前瞻、单结算恒等式、唯一计费、`dt` 与时区口径。
2. **数学正确性**：SOC 动态、CVaR 线性化、缩减概率守恒、MPC 新旧等价。
3. **架构边界**：依赖方向守卫（`domain` 不依赖上层、主链不 import 具体市场模式、活动包不 import 归档）。
4. **兼容回归**：366 项 active-only 基线逐阶段保持绿色。
5. **入口冒烟**：`app/` 全部活动入口最小可运行。
6. **生产数据验收**：真实数据接入、规则标定和收益评估，与样例回归严格区分。
