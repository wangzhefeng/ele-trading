## 1. v6 的定位

### 1.1 与 v3、v5 的关系

| 文档 | 保留的权威范围 | v6 的处理方式 |
|---|---|---|
| [v3](策略算法框架详细设计-v3.md) | D-001～D-007、D-014～D-016 的分层、依赖、事件和 `market_simulation` 独立边界 | 不推翻；v6 的新能力必须遵守这些边界 |
| [v5](策略算法框架详细设计-v5.md) | 已关闭的实施历史、V5-0～V5-11 的原始交付与未退出门 | 未退出项由本文 §9 完整继承；不再作为当前需求或事实入口 |
| **v6（本文）** | 当前事实审计、目标闭环、设计决策、实施顺序和验收标准 | 当前唯一在研设计；根目录与活动文档指针统一指向本文 |

v6 不再以“继续新增预测、优化、仿真模型”为主要目标，而是一次完成下列三类对象的边界与连接：

1. **价格接受者资源运行主链**：外生价格、预测和已知合同/成交约束下的 BESS、DR、风光与负荷组合决策；
2. **离线市场数字孪生**：SCED、SCUC、网络、竞价和行为模型，用于校准、反事实和规则推演，不直接替代线上市场；
3. **真实规则与证据晋级层**：目标市场规则、数据版本、正式账单、影子运行和人工批准。

这一区分来自现货市场的基本事实：电能量市场、辅助服务、计量、偏差、网络安全和结算必须协同，但离线仿真系统不能被误当作生产市场系统；没有现行规则与正式计量/账单，就不能把合成算例解释为真实结算能力。

### 1.2 本次审计范围与证据规则

审计范围为 `src/ele_trading/` 的活动交易、市场、运行、优化、仿真、场景、头寸、回测与用户侧边界。结论分为四级：

| 等级 | 含义 | 本文用语 |
|---|---|---|
| 主链接线 | 常规 `TradingOrchestrator.run()` 消费结果并进入调度或结算 | 已实现能力 |
| 独立算法核 | 有模型、标准算例或单元测试，但主链不消费 | 原型/研究能力 |
| 契约/规则库 | 数据结构、模式协议、公式或 capability 已存在 | 规则骨架，不等于闭环 |
| 缺失 | 没有模型、没有消费链路，或没有真实规则/数据证据 | 算法或证据缺口 |

本次结论不把下列事物当作真实市场事实：

- v5 synthetic fixture、synthetic ledger、synthetic billing、synthetic governance 与其验收报告；
- SCED/SCUC/ABM/MARL 的标准算例；
- 任意未提供正式来源、有效期和目标省份的规则参数；
- 构造的 `BillingStatement` 或优化计划本身。

具体省份的产品定义、申报窗口、价格边界、偏差费、辅助服务、计量口径和结算公式均须以实施时有效的省级规则和市场接口核验。

## 2. 当前实现审计结论

### 2.1 当前真实活动链路

当前 `TradingOrchestrator.run()` 的主链为：

```text
PositionState
  → 多价格 ForecastBundle
  → ScenarioSet
  → provisional 单 BESS 日前计划
  → （可选）Bid → Award 匹配 → 受承诺约束的日前重求解
  → 日内新 vintage + 单 BESS 滚动重优化
  → 单 BESS 实际量结算 / 可选账单对账
```

对应代码证据：

- 多价格角色与 `decision_time` 约束：`trading/orchestrator.py:139-224`；
- 场景构建：`trading/orchestrator.py:295-333`；
- 日前计划：`trading/orchestrator.py:447-483`；
- Award 匹配、累计量限制和日前重求解：`trading/orchestrator.py:485-630`；
- 日内新 forecast vintage、冻结前缀和滚动优化：`trading/orchestrator.py:724-807`；
- 单 BESS 执行量到结算、可选正式账单对账：`trading/orchestrator.py:857-943`。

主链的实际成熟度是：**具有因果时点、计划、部分成交履约约束和工程级计量证据的价格接受者资源优化器**，而不是已接入市场的交易执行系统，也不是完整市场出清系统。

### 2.2 合理且应保留的设计

| 能力 | 当前代码事实 | 合理性判断与适用前提 |
|---|---|---|
| 多价格角色与日内新 vintage | 主链按 `MarketMode` 获取日前/实时价格角色；日内重新发起 price/load/wind/pv 请求 | 合理。符合日前、日内、实时决策的信息集不同这一市场基本要求；前提是 provider 真的按角色返回不同可用数据，而非只给同一曲线贴标签 |
| 物理约束下的日前—日内滚动 | 单 BESS 计划有 SOC、功率、效率、退化、DR；日内冻结执行前缀并按当前 SOC 重解 | 合理。适合价格接受者资源调度；日前计划是基线而非不可变指令 |
| Award 的时点安全 | `receipt_time <= dispatch_decision_time` 才能约束日前；迟到回执只进入未执行日内后缀 | 合理。避免用未来市场回执污染历史决策，也避免重写执行前缀 |
| 外部计量与履约分离 | `ResourceMetering`、`AwardFulfillment` 和 `ResourceExecutionDeviation` 禁止用计划代替实测 | 合理。履约事实必须来自带时区、版本化的外部计量，而不是优化变量 |
| 风险优化内核 | `solve_two_stage_cvar` 显式要求偏差考核参数，构造第一阶段 bid 与第二阶段 recourse | 算法方向合理；市场参数不应隐藏在通用求解器内。但它当前不是主链能力 |
| 多资源 LP | 多 BESS、DR、风光、弃电、电网购电和 CVaR 被统一建模 | 资源聚合数学方向合理；当前仍是独立计划，需要完成运行与结算消费 |
| 事件、结算与对账契约 | Forecast/Bid/Award/Dispatch/Metering/Settlement 事件；账单确认后可自动对账 | 合理。市场系统必须保留输入版本、规则版本、执行与账务证据 |
| 离线 SCED/SCUC 分层 | SCUC 得组合，固定组合后用连续 SCED 取 LMP，uplift 不混入 LMP | 理论方向正确，符合整数组合与边际定价应分开处理的原则；仅限离线物理基线 |
| synthetic-only 资产 | synthetic fixture、模拟账单与验收报告固定 `formal=False` / `production=False` | 合理的工程验证手段；必须永久与正式规则、正式账单和生产资格隔离 |

### 2.3 不合理、未闭合或成熟度不能上调的设计

#### 2.3.1 多资源日内计划仍未成为正式运行和结算对象

当前多资源计划和单 BESS 主计划并行：

- `solve_multi_resource()` 可以输出每个资源的计划、DR、新能源和电网购电：`operations/multi_resource.py:164-485`；
- 编排器可创建 `multi_resource_result` 并将资源级计量与计划比较：`trading/orchestrator.py:631-693`；
- 新增 `MultiResourceIntradayPlan` 可按每资源实际 SOC 重解后缀并做安全裁剪 fallback：`operations/multi_resource_intraday.py:109-181`；
- 但正式 `q_real`、DR 履约、`SettlementReport` 与正式对账仍只从单 BESS `executed_schedule` 计算：`trading/orchestrator.py:857-930`。

因此多资源日内是**并列结果**，不是可执行、可结算的主计划。继续向它增加求解变量不能解决根因；必须把“资源级计划—资源级实测—资源级履约—聚合结算”变成一条唯一运行路径。

#### 2.3.2 交易报价链只完成了工程语义，不具备真实申报能力

当前 `SINGLE_SETTLEMENT_MODE` 明确拒绝正式申报，只支持 `plan-only`：`markets/single_settlement/mode.py:72-97`。`BidSubmission`、`MatchedAward` 和 `AwardedCommitment` 已能验证回执与量/窗口并约束计划，但缺少：

- 经确认市场规则驱动的产品、方向、资格、报价段、申报窗、撤改和幂等语义；
- 除 `energy/sell` 外产品/方向的履约映射；
- Award 短缺到正式偏差费用、违约责任和账单科目的规则映射；
- 已成交资源容量、SOC、DR 或辅助服务可用性的全资源约束。

所以“Bid → Award → Dispatch”只能标为本地工程链，不应被称为目标市场交易策略或正式报价接口。

#### 2.3.3 双结算尚未与主编排和产品语义兼容

双结算引擎要求 `c_daily`、`cpen_dayah`、`cpen_long` 与 `cost_baseline`：`markets/dual_settlement/mode.py:56-79`；主编排却以单结算的 `q_real/p_real/q_long/p_long/p_ref` 参数调用结算：`trading/orchestrator.py:870-917`。双结算还明确没有 DR 产品结算语义：`markets/dual_settlement/mode.py:81-91`。

这不是“换一个 `MarketMode` 即可上线”的插件化能力。v6 必须将市场产品、合同、实际量、偏差与结算的共同输入契约先统一，再实现模式适配器。

#### 2.3.4 场景诊断不在生产决策路径中

`diagnose_scenario_set()` 的明确语义是 `passed=False` 时场景不应进入优化：`scenario/diagnostics.py:1-14`。但代码检索显示该函数没有来自编排器、运行或回测主链的调用；当前场景构建后直接进入日前和日内优化：`trading/orchestrator.py:418`、`735-738`。

并且缺少历史参考时，相关性和极端覆盖会以 `skipped` 方式通过：`scenario/diagnostics.py:173-190`。这对研究探索可接受，对正式候选运行不合理。v6 必须引入明确的 `ScenarioAdmissionPolicy`：试验、synthetic、影子和正式运行分别定义必须项；正式候选不得把关键历史校验静默降级为通过。

#### 2.3.5 市场数字孪生没有完成“物理基线”的必要约束

SCED 已包含 DC 网络、可再生出力、备用裕度短缺变量和 LMP：`market_simulation/sced.py:64-276`。但备用短缺只是以 VOLL 罚项保留可行解，而没有规则驱动的紧急状态、出清拒绝或替代处置。

SCUC 有开机、启动、最小开机、爬坡与 DC 网络：`market_simulation/scuc.py:87-192`，但：

- `Generator` 契约中的 `minimum_down_periods` 与 `shutdown_cost` 没有被 SCUC 消费；
- SCUC 不接收可再生、备用或辅助服务输入；
- N-1 只在独立 `contingency.py` 筛查，未进入 SCUC 可行域；
- SCED 使用单一 `marginal_cost`，没有消费 `OfferStack` 的分段报价；
- `solve_scuc`、`run_n1_screening` 和 `price_from_commitment` 没有交易主链消费者。

它们可作为标准算例和物理研究核，不能称为“安全约束市场出清已完成”。

#### 2.3.6 头寸和报价概率仍是启发式建议

`build_bid_ladder()` 以 `uniform` 或 `linear` 规则构造成交概率：`positions/monthly_trader.py:63-146`。没有订单簿、市场深度、对手行为、报价时点、剩余可用容量或历史成交校准时，这只能是头寸管理建议，不能作为正式报价概率或收益预期。

#### 2.3.7 中长期合同的物理/金融语义没有显式类型

主链把 `q_long × (p_long - p_ref)` 作为合同差价项：`markets/single_settlement/settlement.py:35-47`，并进入日前目标。若合同是金融差价合约，该处理合理；若合同要求分时物理交割、资源绑定或偏差责任，当前模型没有相应的可行域与履约约束。v6 必须让合同类型成为显式规则输入，禁止由字段名推断。

#### 2.3.8 市场时序只约束预测，没有约束全部市场输入

`decision_time` 和 Award receipt time 已防止 forecast/回执前视，但当前没有统一对象定义注册、申报、撤改、出清、调度、计量关账和结算关账的阶段、主体权限、输入 cutoff 与发布结果。市场机制要求这些时点共同决定输入是否可用；只保护预测 vintage 不能阻止迟到计量、修订规则、失效安全校核或越权回执进入后续决策。`MarketTimelinePolicy` 与 `DataAdmissionPolicy` 因此是交易主链的核心语义，不是外围数据清洗。

#### 2.3.9 报价缺少从资源可行域到可提交量价段的优化器

当前 `BidSubmission` 证明本地事件能携带报价，`build_bid_ladder()` 证明可生成启发式建议，但没有同时决定报价量、价格段、资源预留、已成交义务、偏差/短缺风险和信用敞口的规则化优化问题。对电能量、备用、调频和 DR 存在共同资源时，先分别生成梯子再事后裁剪会重复占用资源，不能保证报价可履约。需要将 `BidOptimizationPolicy` 作为 V6-2 的独立算法核，并将当前实现准确保留为 `plan-only`。

#### 2.3.10 价格没有绑定交割位置和安全结果

系统、分区和节点边际价格对阻塞、网损与交割位置的表达不同；当前外生 price role 未携带价格点、交割点或安全校核有效期。离线 SCED 的 DC 网络可用于原型，但不自动说明价格或计划已经过交流潮流、断面、电压和稳定校核。没有 `PricingAndNetworkPolicy`，同一价格曲线可能被错误用于不相同的位置或交割产品；没有获授权的安全结果，任何 `MarketSignalModel` 都不能升格为真实市场安全信号。

#### 2.3.11 真实申报前缺少信用与组合敞口约束

电力市场中的信用、担保、保证金、持仓与产品敞口限制会直接决定“可否提交”，不是结算后的报表字段。当前风险优化聚焦价格和运行成本，未以规则化 `PreTradeRiskPolicy` 阻断超过信用、物理可用量、已成交义务或产品资格的订单。若把该检查留给人工或账后处理，优化器可能连续产生不可提交、不可履约的候选报价。

#### 2.3.12 数字孪生没有市场结构与异常行为风险输出

当前 ABM/MARL 是行为原型，但数字孪生没有输出集中度（例如 CRn、HHI）、剩余供给/关键供应商（RSI/PSI 类指标）、局部阻塞稀缺、经济/物理持留或异常量价的可追溯线索。对于价格接受者资源组合，这些不是线上策略性抬价授权；但它们是判断历史价格是否可外推、何时收紧风险预算、以及何时拒绝将仿真结果用于策略压力测试的必要离线输入。

### 2.4 当前成熟度总表

| 领域 | 当前成熟度 | v6 判断 |
|---|---|---|
| 单 BESS 价格接受者运行 | 主链接线 | 保留并升级为统一资源运行接口的退化路径 |
| Award 约束和外部计量 | 工程级主链接线 | 扩展为规则驱动、多产品、资源级履约与结算 |
| 多资源日前/日内 | 独立计划 + 部分日内接线 | 必须提升为可执行且可结算的主路径，不能继续并列 |
| 单结算 | 主链接线规则核 | 仅适用于确认的单结算市场 profile；当前是 plan-only |
| 双结算 | 规则库 | 必须重构输入与产品契约后才可接入 |
| 场景与 CVaR | 算法核 | 增加准入门并将两阶段报价优化接入已确认的市场模式 |
| SCED/SCUC/N-1 | 离线物理原型 | 先补物理约束与校准，再生成可消费的离线市场信号 |
| ABM/MARL | 离线行为原型 | 不进入线上默认；依赖校准后的物理基线和真实报价数据 |
| synthetic runner/acceptance | 工程证据 | 保持 simulation-only，不能替代真实数据、账单和影子运行 |

## 3. v6 的目标、非目标与设计原则

### 3.1 目标

| 维度 | 当前状态 | v6 目标 |
|---|---|---|
| 运行计划 | 单 BESS 主计划与多资源并列 | 同一资源级计划成为运行、计量、履约和结算的唯一来源 |
| 报价与成交 | 本地工程事件链 | 由市场 profile 驱动的产品、报价、Award、修订、履约和偏差闭环 |
| 合同 | 隐含金融差价项 | 明确金融/物理/混合合同，分别进入风险、可行域与结算 |
| 市场模式 | 以结算接口为主 | 扩展为规则、产品、数据、报价、履约与结算的一致 profile |
| 市场时序与输入准入 | 仅对 forecast `decision_time` 有因果约束 | `MarketTimelinePolicy` 和 `DataAdmissionPolicy` 在申报、出清结果、运行、计量和结算前逐项校验 cutoff、完整性、质量、版本与权限 |
| 报价决策 | `build_bid_ladder()` 以 uniform/linear 成交概率给出启发式建议 | profile 约束的 `BidOptimizationPolicy` 联合优化量、分段价格、资源预留、短缺风险与规则化撤改；无规则和校准不得自动申报 |
| 位置定价与安全结果 | 外生价格无交割点/价格点语义；离线模型仅 DC/N-1 原型 | `PricingAndNetworkPolicy` 显式定义系统/分区/节点价格、交割点、损耗与阻塞口径；真实运行只消费获授权安全校核结果 |
| 交易与市场风控 | 没有信用/担保敞口门；ABM 未形成市场力监测 | `PreTradeRiskPolicy` 阻断超信用/超资源/超产品敞口申报；离线数字孪生输出集中度、局部稀缺与异常行为监测，不将其误称为监管结论 |
| 场景 | 诊断可选、主链未阻断 | 全路径采用可审计的准入门和显式退化策略 |
| 数字孪生 | 多个独立标准算例 | 完整物理基线、离线校准与版本化市场信号输出 |
| 结算 | 单结算主链、双结算规则库 | 产品级计量、账单分项、正式/模拟证据隔离与可复算对账 |
| 验收 | synthetic 工程通过与真实门并存 | 将工程门、真实校准门、影子门和生产门分层执行，禁止跨级表述 |

### 3.2 非目标

- 不把 `market_simulation` 直接嵌入在线交易编排或等待大规模 SCUC/ABM/MARL 训练；
- 不根据 2021 年资料或 synthetic fixture 猜测省级价格限制、偏差费、辅助服务或结算公式；
- 不让 `user_side_dispatch` 进入交易主链；该领域继续独立运行；
- 不因 v6 文档存在而修改默认市场模式、自动申报、生产配置或账单确认状态；
- 不在没有真实网架、报价和规则数据时，将 ABM/MARL 的模拟收益解释为现实收益。

### 3.3 设计原则

1. **市场 profile 先于优化器**：产品、时序、合同、计量、偏差和结算规则必须先有版本化定义。
2. **一份资源计划贯穿到底**：被执行的资源级计划必须是计量、履约、结算和回测唯一来源。
3. **成交是约束，不是日志**：已知 Award 必须投影为资源、产品和时段义务；未知或迟到信息不得回写历史。
4. **安全与价格分开验证**：市场仿真输出只有通过物理约束、校准和数据门后，才能作为交易模型的离线输入。
5. **场景先准入、后优化**：任何准入失败都必须有显式退化、拒绝或停止原因。
6. **规则、数据、账单版本可还原**：一次结算或决策可定位到规则、输入、模型、场景、求解器和计量版本。
7. **全量建设与生产默认分离**：本地工程、真实校准、影子运行和生产晋级是不同的门。

## 4. 目标架构

### 4.1 三层闭环

```text
┌─────────────────────────────────────────────────────────────────┐
│ 真实规则与证据层                                                 │
│ MarketProfile / RuleSnapshot / ProductCatalog / DataCatalog      │
│ GridSnapshot / Metering / Billing / archived vintage             │
└───────────────┬───────────────────────────────┬─────────────────┘
                │                               │
                ▼                               ▼
┌──────────────────────────┐      ┌───────────────────────────────┐
│ 价格接受者资源运行主链    │      │ 离线市场数字孪生              │
│ Forecast → ScenarioGate  │      │ SCUC / SCED / N-1 / ABM        │
│ Position → Bid/Award     │      │ 规则推演 / 校准 / 反事实       │
│ ResourceRuntime → Meter  │      │ 输出版本化 MarketSignalModel   │
│ Settlement → Reconcile   │      │                               │
└───────────────┬──────────┘      └───────────────┬───────────────┘
                │                                  │
                └──────────仅消费已校准信号─────────┘
                                   ▼
                    验收、影子运行、人工晋级
```

`market_simulation` 继续遵守 v3 D-014：不依赖 `trading`、`backtest` 或具体市场插件；线上运行也不直接同步调用仿真器。v6 新增的连接是离线、版本化、可校准的 `MarketSignalModel`，而不是反向依赖。

### 4.2 `MarketProfile`：从结算模式升级为完整市场语义

新增市场 profile 的概念，但不删除现有 `MarketMode`。`MarketMode` 保持主链依赖注入入口；每个模式必须组合已确认的 profile：

```text
MarketProfile
├── market_id / timezone / effective interval / rule_version
├── MarketTimelinePolicy
│   ├── registration / bid / amend / cancel / clearing / dispatch / meter-close / settlement-close
│   └── each phase's cutoff, actor, admissible input version and published output
├── DataAdmissionPolicy
│   ├── source / quality / completeness / revision / permission / late-data semantics
│   └── reject / quarantine / approved fallback and event evidence
├── ProductCatalog
│   ├── energy, reserve, regulation, DR ...
│   ├── direction / unit / delivery granularity
│   └── resource eligibility / bid constraints
├── PricingAndNetworkPolicy
│   ├── system / zonal / nodal price point, delivery location and loss-congestion treatment
│   └── required security-check result, validity window and emergency disposition
├── ContractPolicy
│   ├── financial_difference
│   ├── physical_delivery
│   └── hybrid allocation
├── BidLifecyclePolicy
│   ├── submit / amend / cancel / receipt / idempotency
│   └── bid-window and receipt-time rules
├── BidOptimizationPolicy
│   ├── price-taker / challenger mode, offer segments, quantity, reservation and amendment limits
│   └── objective, risk, calibration and no-auto-submit gate
├── PreTradeRiskPolicy
│   ├── credit, collateral, position, product and resource-availability limits
│   └── reserve / reject / alert / approval semantics
├── CommitmentProjectionPolicy
│   └── product × direction → resource constraints
├── SettlementPolicy
│   ├── day-ahead / real-time / imbalance / uplift / DR
│   └── bill-item mapping and confirmation semantics
└── EmergencyAndFallbackPolicy
    └── data, solver, safety and market interruption handling
```

任何未被 `CommitmentProjectionPolicy` 显式映射的产品或方向必须结构化拒绝，不能按字符串或单 BESS 放电逻辑猜测义务。任何未经过 `DataAdmissionPolicy`、`PricingAndNetworkPolicy` 和 `PreTradeRiskPolicy` 的输入或申报也不得进入正式路径。

### 4.3 统一资源运行对象

v6 采用 `ResourceOperationalPlan` 作为唯一计划语义，替代“单 BESS `OperationalPlan` 为正式计划，多资源结果仅旁路”的状态。

最小组成：

| 子对象 | 内容 | 作用 |
|---|---|---|
| `ResourceSchedule` | 每资源、每时段的充/放、SOC、可用容量、调节量与计划版本 | 执行与冻结前缀 |
| `ResourceActual` | 每资源实测电量、SOC、可用性、质量标记和修订 | 日内状态更新与履约事实 |
| `CommitmentAllocation` | 每 Award × 产品 × 时段 × 资源的承诺分配 | 物理可行域和短缺计算 |
| `PortfolioSettlementInput` | 聚合购电、资源交付、合同量、偏差和费用归属 | 唯一结算输入 |
| `RuntimeFallback` | 数据/求解失败下的资源级安全裁剪、有效时段和原因 | 受控降级 |

单 BESS 不是删除，而是 `ResourceOperationalPlan` 的一个资源数为 1 的兼容实例。多资源 portfolio 启用后，单 BESS 旁路不再可用于正式结算。

### 4.4 场景准入门

新增 `ScenarioAdmissionPolicy`，在 `TradingOrchestrator` 调用任何日前、日内、两阶段或多资源优化之前执行。

```text
ScenarioSet
  → schema / time / probability validation
  → marginal consistency
  → historical correlation and extreme coverage
  → reproducibility check
  → admission decision
      ├── admitted: enter optimization
      ├── degraded: switch to approved lower-tier model
      └── rejected: stop candidate run with event evidence
```

| 运行类别 | 历史参考缺失 | 场景诊断失败 | 允许的结果 |
|---|---|---|---|
| 单元测试 / synthetic | 可标记为 synthetic skipped | 可用于失败反例 | 仅工程证据 |
| 离线研究 | 可显式降级 | 可比较退化模型 | 不产生候选结论 |
| 真实候选回测 | 不允许跳过 | 必须拒绝该样本或使用预注册退化模型 | 可进入经济评估 |
| 影子 / 生产 | 不允许跳过 | 必须告警、降级或中止 | 进入治理记录 |

### 4.5 离线数字孪生的完成定义

v6 不要求仿真器直接参与线上决策，但要求它先具备可信物理基线：

1. SCUC 补齐最小停机、停机成本、初始开停状态跨窗口、备用、可再生、必开必停和规则化不可行处置；
2. SCED/SCUC 对能量、备用和可再生的联合或明确顺序出清进行版本化建模，并记录机会成本；
3. N-1 从事后枚举升级为按 profile 选择的出清前/出清后安全校核与可解释反馈；
4. DC 线性潮流只作为可解释的出清和预筛选模型；真实市场信号发布前必须消费获授权的交流潮流/电压/稳定安全校核结果，或由 profile 明确拒绝该信号。不得把内部 DC 可行解宣称为完整物理安全结论；
5. `OfferStack` 变成真正的分段报价输入，不能继续退化成单一边际成本；
6. 对每次已校准仿真输出集中度（CRn/HHI）、剩余供给/关键供应商（RSI/PSI 类指标）、局部阻塞稀缺和异常量价/持留线索；这些是离线风险信号，不是独立的市场力认定或监管处置；
7. 只有真实网架、检修、报价与保留期校准通过后，才可发布 `MarketSignalModel` 供交易层离线消费；
8. ABM/MARL 只能建立在已校准的 SCED/SCUC 与行为数据上，且仅作为 challenger 或反事实工具。

## 5. 核心算法设计

### 5.1 合同、报价、成交与履约

#### 市场时序、数据准入与申报前风控

市场交易不是“预测完成即优化”的单一函数。每次报价、计划、执行与结算都必须先绑定 `MarketTimelinePolicy` 的市场阶段，并通过 `DataAdmissionPolicy`：

```text
phase cutoff reached
  → verify actor / authority / market calendar
  → verify source, available_at, quality, completeness, revision and rule version
  → verify delivery location / price point / security-result validity
  → verify credit, collateral, position, product and resource availability limits
  → admitted / approved fallback / quarantined / rejected
```

这与 `ScenarioAdmissionPolicy` 互补而不互相替代：前者处理所有市场输入和权限，后者处理已准入预测/场景的统计与物理代表性。任何迟到、越权、质量不合格、价格点不匹配、超过信用或资源敞口的输入必须产生事件证据，不能以旧值、零值或计划值静默补齐。

#### 合同分类

每个合同必须显式选择：

| 类型 | 进入调度可行域 | 进入价格风险与结算 | 当前默认 |
|---|---:|---:|---|
| `financial_difference` | 否 | 是 | 当前 `q_long × (p_long - p_ref)` 的兼容语义 |
| `physical_delivery` | 是 | 是 | 需要目标市场规则后启用 |
| `hybrid` | 按已确认份额 | 是 | 需要 profile 定义分配口径 |

物理合同和 Award 统一转为 `CommitmentAllocation`。对于资源 $r$、时段 $t$ 和卖电能量义务，至少满足：

$$
E^{\mathrm{delivered}}_{r,t} \ge E^{\mathrm{committed}}_{r,t}
$$

但具体可由哪些资源替代、是否允许聚合履约、是否允许偏差结算，必须由产品和规则 profile 决定。

#### Bid 生命周期

```text
Draft
  → Submitted
  → Amended* / Cancelled*
  → Accepted / Rejected
  → PartiallyAwarded* / Awarded
  → Fulfilled / Shortfall / Settled
```

`*` 表示是否允许由目标市场 profile 决定。每个状态事件必须保留：原始 bid、版本、提交/接收时间、有效交割窗口、市场回执、幂等键和规则版本。`synthetic` 生命周期可以用于工程验证，但不得复用为真实 adapter。

#### 报价优化而非报价梯子启发式

`BidOptimizationPolicy` 是**拟议新增**的交易算法，不是当前 `build_bid_ladder()` 的重命名。对产品 $p$、交割时段 $t$、报价段 $k$ 和资源 $r$，它至少决策报价量 $q_{p,t,k}$、报价价格 $b_{p,t,k}$、资源预留量 $a_{r,p,t}$ 与必要的撤改动作；目标是规则许可下的风险调整后预期净收益：

$$
\max \; \mathbb{E}[\text{market revenue} + \text{contract value}
- \text{energy/imbalance/shortfall cost} - \text{degradation cost}]
- \lambda\,\mathrm{CVaR}_{\alpha}(\text{loss})
$$

其可行域至少包含：产品资格、分段单调性、量价步长与上下限、报价窗口、资源可用性、同一资源跨能量/备用/DR 产品的不重复预留、已成交义务、物理合同、信用/担保和已执行前缀。价格接受者默认只允许使用经过 profile 和保留期校准的量/可用性策略；价格形成、对手响应和策略性报价仅可在 V6-4 的离线 challenger 中研究。没有当前规则、成交数据和校准证据时，输出必须停留为 `plan-only` 建议，不得自动提交。

### 5.2 统一资源级日前—日内优化

资源组合优化需在同一模型中处理：

- BESS：SOC、效率、功率、终端 SOC、退化、可用容量和不可同时充放；
- DR：基线、可调用量、回补、产品窗口、响应失败和补偿/罚则；
- 风光：forecast vintage、可用容量、限电和修订；
- 合同与 Award：资源/时段/产品义务、替代范围、已执行前缀；
- 电网购电与负荷：聚合平衡、负荷误差与价格角色；
- 风险：经场景准入的成本、履约短缺和尾部风险。

日内状态必须来自资源级实际输入：

```text
上一轮 ResourceOperationalPlan
+ 实际计量 / SOC / 可用性 / Award 修订
+ 新 forecast vintage / 新 ScenarioSet
→ 冻结实际已执行前缀
→ 重解未来后缀
→ 资源级 fallback 或结构化失败
```

目前 `MultiResourceIntradayPlan` 只接收实际 SOC、冻结的是上一计划前缀。v6 要求实际充放、DR 响应、可再生出力和资源可用性也进入后缀初值与履约约束，禁止以原计划代替已执行实绩。

### 5.3 价格、场景与风险

保留已有 DA/RT/长期价格角色，但将模型选择改为以真实规则 profile 和经济价值约束：

1. 日前参考、日前结算、实时结算和价差保持不同 target；
2. `MarketStateForecast` 只在状态特征定义、数据可用时刻、规则版本和概率校准均明确时使用；
3. 场景集必须联合保留价格、负荷、风光及其依赖；
4. 极端模板、缩减保护、重要性采样或对抗压力不得使用无来源概率；
5. 模型晋级标准为保留期风险调整后结算改善，而不是单独 MAE/Pinball 改善；
6. `solve_two_stage_cvar` 在 profile 提供日前/实时结算与偏差规则后，作为正式报价策略候选接入；在此之前保持离线算法核。

### 5.4 市场仿真输出给交易层的边界

交易层只允许消费已发布、可追溯的离线信号，例如：

| 信号 | 来源 | 可用于 | 不可用于 |
|---|---|---|---|
| 价格分布/基差情景 | 校准后的 SCED/SCUC 或历史模型 | 场景压力、风险预算 | 替代正式出清价 |
| 阻塞/备用风险状态 | 校准后的网架与规则模型 | 市场状态特征、资源预留 | 未校准时直接触发报价 |
| 对手响应范围 | 校准 ABM | 报价 challenger、压力测试 | 线上自动策略 |
| policy guard 结果 | 受控 MARL 评估 | 拒绝不安全 challenger | 自动切换生产默认 |

这既遵守 v3 的独立边界，也避免“SCED/SCUC 不被主链调用”被误解为必须把求解器在线耦合。

### 5.5 结算、对账和经济验收

结算输入按四层分开：

```text
Market result      : bid / award / clearing price / product
Resource actual    : metering / availability / SOC / revisions
Contract ledger    : physical / financial commitments
Rule profile       : settlement items / imbalance / uplift / DR / tax-fee
```

目标市场的 `SettlementPolicy` 必须输出逐项账务映射：

| 科目 | 数据来源 | 是否可由通用公式推断 |
|---|---|---|
| 电能量 | 计量 + 出清/结算价 | 否，取决于市场模式 |
| 日前—实时偏差 | 已成交计划 + 实际量 + 规则 | 否 |
| 合同差价 | 合同类型 + 参考价 + 规则 | 仅金融合同可采用通用差价骨架 |
| DR/辅助服务 | 承诺、性能计量、产品规则 | 否 |
| uplift、阻塞盈余、运营费 | 出清/结算规则 | 否 |
| 退化与内部执行成本 | 资源模型 | 是，但与正式市场账单分列 |

`synthentic` 或 `confirmed=False` 的账单只能产出工程对账；正式经济验收要求已确认账单和完整规则版本。

### 6.3 需要用户确认的市场输入

下列输入不是编码细节，缺失时相关实现只能保持 profile 骨架或 `plan-only`：

1. 目标省份/市场、主体角色（用户、售电、聚合、发电或储能）和产品范围；
2. 中长期合同的物理/金融属性、交割曲线、偏差与资源绑定规则；
3. 日前、日内、实时和辅助服务的申报窗口、修改规则、回执字段、时区和粒度；
4. 价格边界、量价段、最小量、资格、信用和异常处置规则；
5. 系统/分区/节点价格机制、交割位置、网损/阻塞口径，以及出清结果所需的安全校核结果、有效期和应急接管规则；
6. 信用、担保、保证金、持仓/产品敞口限额及超限的审批、拒绝和恢复规则；
7. 双结算/偏差/DR/辅助服务/uplift 的正式账单分项和确认口径；
8. archived forecast vintage、网架/检修、报价成交、资源计量和正式账单数据的来源、许可、owner 与保留期；
9. 影子运行的运行窗口、champion、回滚责任人和人工审批流程。

## 8. 验收与成熟度门

### 8.1 四层证据

| 层级 | 允许的证据 | 不允许宣称 |
|---|---|---|
| 工程 | 单元、契约、结构、synthetic、标准算例 | 真实市场、正式结算、生产可用 |
| 物理 | 可信网架与规则下的 SCED/SCUC/N-1 回放 | 真实报价行为已校准 |
| 经济 | archived-vintage 保留期、正式账单对账、风险统计 | 生产稳定运行 |
| 生产 | 影子、漂移、回滚演练、人工批准 | 自动永久晋级 |

### 8.2 v6 必测反例

- receipt 晚于本次决策时点，不能改变执行前缀；
- 部分成交累计超过 bid、交割窗口越界、产品/方向未映射，必须拒绝；
- 物理合同量无法由允许资源覆盖，必须透明失败或执行已授权偏差路径；
- 多资源实际 SOC、可用性或计量修订与计划不一致，日内后缀必须使用实际状态；
- 场景概率、历史相关或极端覆盖未通过时，正式候选不得求解；
- 市场阶段、输入版本、数据质量、主体权限、价格点/交割点或安全校核有效期不满足时，申报、运行或结算必须拒绝或进入已授权 fallback；
- 报价段不满足最小量、步长、单调性、产品资格、资源可用性、已成交义务或信用/担保限制时，`BidOptimizationPolicy` 必须拒绝而非裁剪为可提交报价；
- SCUC 最小停机、备用、网络事故或分段报价约束不可满足时，不能提取伪造价格/出清；
- 内部 DC 预筛选通过但没有获授权 AC/电压/稳定安全结果时，不得发布可被当作真实安全出清的 `MarketSignalModel`；
- synthetic statement 即使内部对账一致，也必须保持 `confirmed=False`；
- 双结算没有完整规则输入时必须结构化失败，不能退化为单结算公式；
- 任何账单对账差异、约束违约、硬反例失败或漂移超限，候选不得晋级。

### 8.3 性能与透明性

性能预算沿用 v3/v5 的“规模 × 时限 × 失败率”口径，但新增：

- 多资源日内后缀在给定资源数、场景数和时段数下的 wall-clock、fallback 率与 SOC 违规数；
- 市场 profile 验证、产品映射和账单重算的 deterministic replay 时间；
- SCUC 的 MIP gap、超时、约束松弛、备用短缺和 N-1 失败率；
- 影子账单差异、迟到数据率、vintage 缺失率和规则版本漂移。

求解失败、对偶不可用、规则缺失、场景拒绝和账单不确认均必须生成可追溯状态；不得使用默认零值、静默裁剪或可伪造布尔值伪装成功。
